# Dittofeed Lite Performance Test Report

## 1. Executive Summary

Dittofeed Lite was tested in GitHub Codespaces with synthetic transaction events generated by k6. The test set included manual API verification, E2E verification, load, stress, spike, a shortened soak test, Docker resource monitoring, and OOM/restart checks.

Main findings:
- 10 RPS / 2 min passed the defined HTTP latency thresholds.
- 15 RPS violated the p95 < 150 ms SLO.
- 20 RPS violated p95 and introduced dropped iterations.
- 25 RPS showed stronger degradation: p95 271.90 ms, p99 2.97 s, 48 dropped iterations.
- A spike of ~40 RPS total produced p95 373.78 ms, p99 656.35 ms, 3 dropped iterations, and the first HTTP error.
- A shortened 10-minute soak at 10 RPS produced p95 244.74 ms and post-test E2E latency of 108 s.

The observed SLO boundary is therefore between approximately 10 and 15 RPS. Stronger saturation indicators begin around 20 RPS in this Codespaces environment. These results are environment-specific and are not universal Dittofeed capacity limits.

## 2. Environment

- Platform: GitHub Codespaces
- Deployment: Dittofeed Lite via Docker Compose
- Services: Dittofeed Lite, PostgreSQL, ClickHouse, Temporal
- k6: v2.2.0 via official `grafana/k6` Docker image
- Test data: synthetic only

## 3. Test SLOs

- `http_req_failed < 0.1%`
- `p95 HTTP latency < 150 ms`
- `p99 HTTP latency < 500 ms`
- `dropped_iterations = 0`
- `checks > 99.9%`

HTTP ingestion latency and E2E background-processing latency were evaluated separately.

## 4. Manual API Verification

Before load testing:
- Admin API authentication returned HTTP 200.
- Synthetic `identify` returned HTTP 204.
- Synthetic `track` returned HTTP 204.
- Admin API lookup confirmed `test-0001` and computed property `city = Chisinau`.

This proved that ingestion requests were not only accepted but also processed by the background system.

## 5. E2E Probe

A custom E2E probe was implemented. It:
1. sends an `identify` event with a unique user ID;
2. polls the Admin API;
3. waits for `city = Chisinau`;
4. records elapsed time.

Baseline E2E latency: **45 s**.

## 6. Results

| Scenario | Load | p95 | p99 | HTTP errors | Dropped | E2E |
|---|---:|---:|---:|---:|---:|---:|
| Baseline | idle | - | - | - | - | 45 s |
| Load | 10 RPS / 2 min | 92.47 ms | 126.25 ms | 0% | 0 | 74 s |
| Load | 15 RPS / 2 min | 237.80 ms | 255.14 ms | 0% | 0 | 69 s |
| Load | 20 RPS / 2 min | 236.69 ms | 277.81 ms | 0% | 3 | 49 s |
| Load | 25 RPS / 2 min | 271.90 ms | 2.97 s | 0% | 48 | 48 s |
| Stress | ramp 5→25 RPS / 4 min | 243.29 ms | 294.69 ms | 0% | 0 | 70 s |
| Spike | 10 RPS + 30 RPS spike | 373.78 ms | 656.35 ms | 0.03% | 3 | 35 s |
| Soak | 10 RPS / 10 min | 244.74 ms | 292.13 ms | 0% | 1 | 108 s |

## 7. Saturation Analysis

The short 10 RPS load test passed all HTTP thresholds.

At 15 RPS, p95 increased to 237.80 ms and violated the SLO even though no iterations were dropped. This shows that latency degradation begins before obvious capacity loss.

At 20 RPS, p95 remained above the SLO and 3 iterations were dropped.

At 25 RPS, tail latency degraded sharply and 48 iterations were dropped. Therefore:
- **SLO boundary:** approximately 10–15 RPS.
- **Stronger saturation signal:** approximately 20 RPS and above.

## 8. Stress and Spike

The ramping stress test supported the same conclusion: aggregate p95 was 243.29 ms while HTTP errors remained at 0%.

The spike test was more severe. During a 10 RPS baseline plus 30 RPS spike:
- p95 = 373.78 ms
- p99 = 656.35 ms
- dropped iterations = 3
- HTTP error rate = 0.03%

This was the first scenario that produced an HTTP request failure.

## 9. Soak

A shortened 10-minute soak at 10 RPS produced:
- 5999 successful requests
- p95 = 244.74 ms
- p99 = 292.13 ms
- 1 dropped iteration
- post-test E2E = 108 s

The same 10 RPS rate had passed the short 2-minute load test with p95 = 92.47 ms. The longer run therefore exposed degradation that was not visible in the short run.

Limitation: a 10-minute soak is shorter than the 30+ minutes recommended for stronger long-duration conclusions.

## 10. Resource Observations

During the soak:
- Dittofeed Lite: approximately 511–529 MiB / 1 GiB (~50%)
- ClickHouse: approximately 957–995 MiB / 2 GiB (~47–49%)
- Temporal: approximately 103–106 MiB
- PostgreSQL: approximately 100–102 MiB
- one ClickHouse CPU sample reached ~30.96%

OOM/restart checks:
- ClickHouse: OOMKilled=false, Restarts=0
- Dittofeed Lite: OOMKilled=false, Restarts=0
- PostgreSQL: OOMKilled=false, Restarts=0
- Temporal: OOMKilled=false, Restarts=0

The collected resource evidence is not sufficient to claim a single confirmed internal bottleneck.

## 11. E2E Observations

Observed E2E values:
- baseline: 45 s
- after 10 RPS: 74 s
- after 15 RPS: 69 s
- after 20 RPS: 49 s
- after 25 RPS: 48 s
- after stress: 70 s
- after spike: 35 s
- after soak: 108 s

The values are not monotonic with load, so a single E2E point should not be treated as proof of a bottleneck. The 108 s result after sustained load is nevertheless important and should be repeated with multiple concurrent probes.

## 12. Issues Found

- Initial `WRITE_KEY` contained only the `Basic` prefix, causing HTTP 401 `InvalidWriteKey`. The full value was stored locally afterward.
- `uuidgen` was unavailable; `/proc/sys/kernel/random/uuid` was used instead.
- An initial GET request to `/api/admin/users` returned a Next.js 404 page. The working call was `POST /api/admin/users/` with `workspaceId` and `userIds` in JSON.
- Docker Compose reported an obsolete `version` attribute warning; it was non-blocking.

## 13. Bottleneck Assessment

Performance degradation is repeatable, but the exact internal bottleneck is not proven.

Evidence:
1. p95 exceeds SLO from 15 RPS.
2. dropped iterations begin at 20 RPS.
3. p99 rises sharply at 25 RPS.
4. the spike produces the first HTTP error.
5. E2E reaches 108 s after the shortened soak.

Counter-evidence against a simple memory/OOM explanation:
- no OOM events;
- no container restarts;
- memory remained below configured limits;
- sampled CPU does not prove sustained saturation.

Conclusion: a repeatable performance boundary was found, but root-cause attribution requires additional Temporal, ClickHouse, and worker telemetry.

## 14. Recommended Next Steps

1. Repeat load levels several times.
2. Run a full 30–35 minute soak.
3. Run multiple concurrent E2E probes and calculate p50/p95/p99.
4. Collect Temporal task-queue backlog and workflow latency.
5. Collect ClickHouse query latency and CPU/IO metrics.
6. Correlate k6 timestamps with service metrics.
7. Re-test the 10–15 RPS range with smaller increments.

## 15. Conclusion

Dittofeed Lite accepted synthetic traffic with very low HTTP error rates, but successful ingestion alone did not guarantee acceptable performance. The short 10 RPS test passed the HTTP SLO, while 15 RPS already violated p95. Stronger saturation indicators appeared from around 20 RPS, and the spike scenario produced both tail-latency degradation and the first HTTP error.

The main QA conclusion is that HTTP latency, dropped iterations, resource usage, and E2E background-processing latency must be evaluated together.
